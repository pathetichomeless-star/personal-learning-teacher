## 3. Mandated attacks (directive §26) — one by one, with evidence

**Attack 1 — 1000-frame clean run, ~1 ms scheduling overshoot: does the pacer converge to ~50 fps rather than 47.4?**
YES. Own simulator (A.5:435-448 implemented literally: `deadline_n = epoch + n*20`, `not_before = max(deadline_n, prev_start + 18)`, `prev_start ← send_start` on success), 1000 frames, `j ~ |N(1.0, 0.3)|`: mean interval **20.0001 ms ⇒ 50.000 fps**, min interval 18.572 ms. With the mock envelope resampled (E[δ]=1.386 < slack 2): **19.9998 ms ⇒ 50.001 fps**. Contrast: the legacy pacer (`turns.py:588-591` sends then sleeps 20 ms) yields the measured 21.0939 ms ⇒ 47.407 fps. So the fix is real *provided* `E[j] < 2 ms`. FAILURE MODE FOUND: on the r1d/r1e envelopes (E[δ] = 3.298/2.472) the same code gives **46.21 / 48.15 fps** ⇒ BLOCKER B2.

**Attack 2 — a single 3 ms late wake: does the next interval recover without dropping below 18 ms?**
YES. Injected `j = [1×10, 3, 1×10]`: intervals `… 20.000, 22.000, 19.000, 19.000, 20.000 …`, min = **19.000 ms ≥ 17.999**, and the rate returns to 20.000 ms. The algebra: `L_n = max(0, L_{n-1} − 2) + j_n` (slack 2 = 20 − 18), `interval_n = 20 + j_n − min(L_{n-1}, 2) ∈ [18, 22]` for j ≤ 2. Note the corollary: recovery depth is bounded by the slack (2 ms/frame), which is exactly why a *sustained* `E[j] > 2` sags (B2).

**Attack 3 — a 10 ms `send_bytes`: visible slow-send/rebase rather than a burst?**
Design-wise YES: `send_call_duration_ms = 10 > SLOW_SEND_THRESHOLD_MS = 5.0` ⇒ `slow_send_events += 1`, no catch-up, next deadline rebased from completion, next send ≥ completion + 18 ms ⇒ next interval ≥ 28 ms ⇒ **no burst** (A.5:452-454). The burst is structurally impossible anyway (`not_before ≥ prev_start + 18`, A.5:439-441). TWO DEFECTS: (i) the "next send ≥ completion + 18" half of this guard has no representation in the specified state/pseudocode — implementing A.5:437-448 literally can start the next send as early as `prev_start + 18 = completion − T + 18` (for T=10: completion + 8 < completion + 18) if the §2 rebase lands the new deadline below that; (ii) the §2 slow path bypasses A.6's `MAX_REBASE_LATENESS_MS = 250` bound entirely (the rebase resets `lateness_n` to ~0 so Case B never fires), so an arbitrarily long slow send produces neither a fatal stall nor an INVALID run and `slow_send_events` is reported-only (A.15 row 2) ⇒ the run can still PASS. See MAJOR M1. Reachability: `max T = 0.214 ms` in all three evidence bundles, so this branch never fires on the observed path — it is a latent branch, not an observed one.

**Attack 4 — barge-in lands in `RESERVED_WAIT`: known flush, `unknown = 0`?**
YES. A.4.C:373 maps RESERVED_WAIT + barge-in to **known-unsent** ⇒ `flushed_bargein_frames`; only a cancellation delivered *after entering SEND_AWAIT* can create `send_outcome_unknown_frames` (A.4.C:374-375); A.10:648 states "barge-ins land in the suspended-wait window in practice, so `send_outcome_unknown_frames == 0` is the expected reading". `barge_in_sequence_incomplete` stays 0 if all four bits succeed (A.10:645). RESIDUAL AMBIGUITY (MINOR m3): A.10 does not say whether the RESERVED_WAIT head frame is resolved by BIT1 (pacer cancel) or BIT2 (store flush); A.6:543 splits those two steps explicitly, A.10 does not, so a double-count into `flushed_bargein_frames` is possible in implementation and would surface as a row-8 residual.

**Attack 5 — barge-in inside `SEND_AWAIT`: outcome-unknown + run INVALID?**
YES. A.4.C:374 "Only a cancellation delivered **after entering `SEND_AWAIT`** may create `send_outcome_unknown_frames += 1` (retaining its INVALID consequence for zero-loss acceptance)"; A.15 row 9 makes `send_outcome_unknown_frames = 0` a validity precondition; A.13:789 declares the close-during-send scope and requires those runs to be labelled. No gap found. (Also reinforced by A.10:648's witness wording, which correctly places the synchronous stretch after the wait inside the transport await.)

**Attack 6 — five terminal paths (`listen_start` / upstream-close / send-error / fatal-stall / byte-cap): are both the frame domain and the residue domain closed and balanced?**
Balanced on all five, by construction, because every path (i) invalidates + clears `current_resp_id` (A.4.A:271), (ii) resolves QUEUED **and** RESERVED_WAIT frames into exactly one reason bucket, (iii) resolves an in-flight `SEND_AWAIT` head into `send_outcome_unknown_frames`, and (iv) routes the residue into exactly one `residue_discarded_<reason>_bytes`. Explicit per-path evidence: fatal stall — A.6:542-549 steps 1-8 (step 2 splits PRE_SEND_WAIT vs SENDING, step 3 residue, step 4 end-marker, step 5 cancel-once, step 6 one stop); byte-cap — A.11:677-683; send-error — A.4.C:377; listen_start / upstream-close / abort / close / barge-in — A.4.C:373 + the 8-reason set (A.4.B:332) + A.14's per-reason counters. All nine buckets appear on both sides of the row-8 equation (A.4.C:384-397) and the row-7 equation (A.4.B:305-327); quiescence forces `still_stored_frames = in_flight_frames = 0` and `still_buffered_pcm_bytes = 0` (A.4.C:400-405). TWO GAPS: (a) the legacy flush call sites and the `qwen_closed` → `UPSTREAM_CLOSED` rename are not enumerated (MINOR m4); (b) the seal-time path has an *unclosed* residue/tail case — the "sixth" path (normal seal at a full backlog; see B1) is exactly where this attack finds a hole. Verdict: 5/5 balanced, but the seal path is not.

**Attack 7 — STORE_CAP transition with `dl_buf` already holding 500 admitted bytes: disposed exactly once, no double counting?**
YES, by A.2's rules (A.2:189-201). Trace with the document's own numbers (A.2 test B, A.2:208): `unsent_backlog_frames = 1500`, `dl_buf = 500` (all 500 already in `admitted_pcm_bytes`), triggering delta of `D ≥ 460` bytes: (1) fire `AUDIO_STORE_CAP_REACHED` exactly once; (2) `residue_discarded_store_cap_bytes += 500`; (3) `dl_buf.clear()` ⇒ `len(dl_buf) = 0`; (4) all `D` bytes ⇒ `safety_truncated_pcm_bytes` (none admitted); (5) later deltas likewise. Source closure: the 500 sit in `admitted_pcm_bytes` (once) and in `residue_discarded_pcm_bytes` (once) — that is the normal in/out structure of the equation, not a double count; the 500 appear in exactly one *residue* counter. Framer closure: `admitted ⊇ 500` is balanced by the `residue_discarded_store_cap_bytes = 500` term; the `D` bytes never enter `admitted`. Frame domain: no frame is formed or refused, so nothing enters `encoded_full_frames`; `residue_discarded_store_cap_bytes` owns no frame bucket (A.4.B:332) ⇒ row 8 untouched. INVARIANT: `0 <= len(dl_buf) < 960` holds at every instant because the transition fires as soon as `len(dl_buf) + len(delta) >= 960` while the backlog is 1500 (A.2:192, A.2:200) — uncontradicted (A.3:250). Also verified the *non*-firing case: backlog 1500, `len(dl_buf) + len(delta) < 960` ⇒ bytes admitted into the residue, no transition, no truncation. VERDICT: exactly-once disposal confirmed; no double counting. (The separately-failing seal case is B1, not this.)

**Attack 8 — tail-frame encode failure: is normal-completion PASS necessarily denied?**

## 4. BLOCKERS

### B1 — The normal-seal synthetic tail has **no disposition** when the unsent backlog is full: A.9 unconditionally mandates a tail frame that the frame cap forbids admitting, and rev 6's §8 rewrite deleted the only rule that used to cover it.

**Evidence (Part A).**
- A.9:607 (`Normal completed response`, step 1): "process the final residual — `N == 0` → no synthetic tail; **`0 < N < 960` → one synthetic tail frame** (encode-failure path per A.4.B)". A.4.B:335 repeats it unconditionally and even removes the legacy `len >= 2` shortcut (`turns.py:424`).
- A.2:187 (admission rule): "a new complete frame may be admitted **only** when `unsent_backlog_frames + 1 <= MAX_FUTURE_FRAMES`" with `MAX_FUTURE_FRAMES = 1500` (A.2:182) and `unsent_backlog_frames = queued_frames + in_flight_frames` (A.2:180).
- A.2:189-201 defines the **only** exit from the "backlog == 1500 with a non-empty `dl_buf`" state: the decision is evaluated **per incoming delta** ("The decision is evaluated per incoming delta, before any of that delta's bytes are admitted: if `len(dl_buf) + len(delta_bytes) >= 960` while `unsent_backlog_frames` is still 1500 …"). A synthetic tail formed at **seal** time is not an incoming delta, so no clause applies to it.
- A.9:615 ("`CONTROLLED_TAIL_TRUNCATION`") only covers the case where the transition *already fired* ("the residue was already discarded at the transition (A.2), so there is **no** synthetic tail for this generation"). It explicitly does not cover a full backlog that never fired a transition.
- A.14 has **no** `residue_discarded_cap_bytes` any more (only `residue_discarded_store_cap_bytes`, A.14:827); rev 5's A.2 rule for the frame-cap-boundary candidate ("the refused candidate is never encoded; all bytes then in `dl_buf` … are discarded as `residue_discarded_cap_bytes`", §0.5 row B1) was **deleted** by the §8 rewrite, and with it the only bucket that could have taken these bytes.
- A.3:250 asserts the invariant `0 <= len(dl_buf) < 960` "at every instant", and A.2:191 explicitly permits a residue to remain buffered "until enough new source bytes arrive" — i.e. the design contemplates the precondition of this hole.

**Scenario (reachable).** Pacer stalled (A.6 Case A rebase, or a §2 slow/blocked send, or simply the pacer being slower than the arrival rate for a while — this is precisely what the frame cap exists for): the backlog reaches 1500 with the 1500th admission leaving a residue `R` in `dl_buf`, `1 <= R <= 959` (the leftover of the delta that completed frame 1500; A.4.C:364-368 keeps `dl_buf` sub-frame). Qwen then sends `response.audio.done` **before** the next audio delta. Normal seal (A.9:607) ⇒ residual `N = R` ⇒ A.9 mandates exactly one synthetic tail frame belonging to this generation.

**Why both readings are defects.**
- If the tail frame **is** admitted (a natural implementation of A.9 step 1): `unsent_backlog_peak_frames` becomes **1501**, breaking A.15 row 4 (`<= 1500`), A.2's admission rule (A.2:187) and A.2 test B's "canonical peak `unsent_backlog_peak_frames == 1500`" (A.2:208).
- If the tail frame is **refused**, nothing in Part A says where the `R` bytes go. `admitted_pcm_bytes` already contains them (they were admitted when their delta arrived, A.4.A:286 + A.2:192), so A.4.B's framer closure (A.4.B:305-311) leaves a **residual of R** unless they enter some residue bucket; the only candidate, `residue_discarded_store_cap_bytes`, is defined solely for a delta-triggered transition (A.2:194). A row-7 (A.15 #7) residual then makes a perfectly legal run fail acceptance — or, worse, an implementer silently drops the bytes, which is exactly the "silent media loss" the whole three-domain accounting exists to prevent (`audio_rebase_discarded_frames`-style invariant).

**Impact.** This is a hole in the *primary* accounting guarantee (no frame and no byte unclassified) at the *most common* terminal path (normal seal), reachable without any pathological scheduling — any response whose seal coincides with a full backlog and a partial residue. It is also a **regression introduced by rev 6**: rev 5's A.2 had a refused-candidate rule that covered this case; directive §8's wording (delta-scoped only) replaced it without a seal-time clause.

**Minimal fix (one of two, both small).** State normatively in A.2 (and reference it from A.9 step 1 and A.4.B): *at seal, if the synthetic tail frame cannot be admitted because the backlog is full, the residue `N` is disposed of through the A.2 store-cap rule — `AUDIO_STORE_CAP_REACHED` fires once for that generation, `residue_discarded_store_cap_bytes += N`, `dl_buf.clear()`, no synthetic tail frame is created, and `synthetic_tail_frames`/`synthetic_tail_source_bytes` are not incremented* (alternatively re-introduce a named frame-cap-boundary residue bucket); and add the mirror case to A.2's clear-site list (A.4.B:333) and to the test table as **test B′**: "seal with backlog == 1500 and `0 < len(dl_buf) < 960`".

**Exit criterion.** A.2/A.9/A.4.B assign that residue to exactly one named counter; test B′ exists and asserts `residue_discarded_store_cap_bytes == N`, `unsent_backlog_peak_frames <= 1500`, no synthetic tail frame, `cap_transitions_max_per_generation <= 1`, and framer/source/disposition residuals 0 (guarantee: `still_buffered_pcm_bytes == 0`, `in_flight_frames == 0` at quiescence).

### B2 — The directive-mandated floor (`MIN_SEND_START_INTERVAL_MS = 18.0`) makes the directive-mandated rate gate (`steady_pacer_rate_fps ∈ [49.5, 50.5]`) fail on the two real measured envelopes; the document's only remedy contradicts directive §1, and the document leaves both values standing.

**Evidence (the document's own numbers, independently reproduced).**
- Slack = `20 − 18 = 2 ms` (A.5:469, A.1:162). The drift condition `E[j] < slack` is stated normatively by the document itself (A.1:162, A.5:469) and is mathematically the Lindley stability condition for `L_n = max(0, L_{n-1} − 2) + j_n`.
- Measured `E[δ]`: **1.386 / 3.298 / 2.472 ms** (my recompute, §1(d); A.16:944 states 1.39 / 3.31 / 2.47). ⇒ the condition fails for **both** instrumented real envelopes (and A.16:946 admits it: "the slack precondition is load-bearing").

- The remedy offered (A.1:162, A.5:469) is "widen the floor (e.g. 15–16 ms) … this is a parameter decision, not a structural change" — while §0.6 row 1 claims directive §1's `MIN_SEND_START_INTERVAL_MS = 18.0` is applied **verbatim**, A.5:428 states `MIN_SEND_START_INTERVAL_MS = 18.0` as the normative constant, A.5:467 calls the target cadence 20 ms/50 fps, and the directive (per §0.6 row 1) *is* the source of the value.
- Aggravating: the acceptance gates themselves require the instrumented configuration (`tts_playout_*` client metrics, A.13:783-784; the bridge fields live in `/health`, A.14:791). The document labels the *un*-instrumented/simulated envelope as "clean/mock" (A.16:944) — i.e. the configuration with `E[δ] < 2` is the one with the least evidence, and the document never pins which environment the "clean long-response acceptance run" (A.13:774) must be executed on.

**Why this is a BLOCKER and not a documented risk.** (i) The gate is mandatory and non-negotiable in the directive (§3, §0.6 row 3, A.15 row 2); (ii) the design's *primary success claim* — A.1:154 "the pacer changes are specified to **restore the 50 fps media rate** (with the two-sided positive-rate gate)" — is falsified on the measured evidence with the mandated constant; (iii) the document does not resolve the conflict: an implementer cannot tell whether 18.0 or 15–16 is the value to ship, and either choice breaks a different normative clause (18.0 ⇒ row 2 fails; 15–16 ⇒ §0.6 row 1's "verbatim" claim and A.5:428 are violated). A design that gates implementation cannot leave its acceptance parameter undecided and its acceptance criterion unachievable on its own evidence.

**Minimal fix (pick one and make it normative, not advisory).**
1. **Amend the floor by derivation and say so**: make `MIN_SEND_START_INTERVAL_MS` a *derived* constant `= 20 − (measured mean overshoot + ≥1 ms margin)`, with the directive's 18.0 stated as the hard lower bound, and record the acceptance-config measurement that fixes it (this needs the directive/human to authorise the deviation, and A.5:428 + §0.6 row 1 must be reworded accordingly); **or**

**Exit criterion.** Exactly one normative value of `MIN_SEND_START_INTERVAL_MS` appears in Part A and §0.6 row 1 is consistent with it; A.1/A.5's "widen the floor" text is either removed or promoted to a normative parameter decision with an explicit configuration statement; and the acceptance configuration is named, with `E[j] < slack` demonstrated (a measured `pacer_wake_overshoot_mean_ms_observed` below the slack on that configuration) or the gate's domain restricted accordingly.

## 5. MAJORS

### M1 — Directive §2's slow-send guard is not implementable from the specified state/pseudocode, is unbounded relative to A.6's stall bound, and can leave the rate gate vacuously satisfied.

**Evidence.** §0.6 row 2 (A.5:452-456) requires: success with `send_call_duration_ms > 5.0` ⇒ "rebase the next media deadline from the observed completion time; the next audio send may not start before `completion_time + MIN_SEND_START_INTERVAL_MS`". But the normative pacing loop (A.5:437-448) computes `not_before = max(deadline_n, normal_floor, send_guard_until or −infinity)` with `normal_floor = previous_audio_send_start_at + 18` (A.5:439) and the state list (A.5:476-479, A.14:868-870) contains only `previous_audio_send_start_at` and `send_guard_until` (the latter set only on *failure/unknown*, A.5:455). Nothing records `completion + 18` for a slow **success**, and `previous_audio_send_start_at` is set to the send **start** "NEVER the send-completion time" (A.5:446). Implementing the pseudocode literally: with `T = 10 ms` and a rebase target `= completion` (the literal reading of "rebased from the completion time"), the next frame's `not_before = max(completion, start + 18) = start + 18 = completion + 8` — i.e. **8 ms** after the slow send completed, violating the stated 18 ms guard. Second: the §2 rebase resets `lateness_n ≈ 0` before A.6's `lateness_n > MAX_REBASE_LATENESS_MS = 250` test (A.6:521,538), so a multi-second slow send produces **neither** `PACER_FATAL_STALL` (A.6:540) nor an INVALID run; `slow_send_events` is "reported" only (A.15 row 2) and is in no PASS clause (A.15 row 22) — a run plagued by slow sends can PASS. Third: the rebase's numeric target is undefined, so the realized post-slow cadence (28 / 30 / 38 ms) and the `wire_rate_excess_frames_max` margin are implementation-dependent. Fourth (related loophole): if slow‑send rebases split the run such that **no** clean segment of ≥250 frames exists (A.5:458), `steady_pacer_rate_fps` / `pacer_mean_inter_send_ms_observed` have no value and A.15 row 2 is satisfied vacuously; A.5 states the ≥250 requirement but no fallback verdict, and rev-5's "shorter runs are information only" rule survives only in superseded §0.5.

**Impact.** A mandated behaviour (§2) is unrepresentable as specified (implementation-defined at best), an unbounded stall class escapes A.6's bound, and the primary rate gate has a vacuous-pass loophole. Reachability on the measured path is low (`max T = 0.214 ms`, §1(a)) — this is a latent-branch and specification-integrity defect, hence MAJOR rather than BLOCKER.

**Minimal fix.** Add one connection state, e.g. `send_guard_until = completion + MIN_SEND_START_INTERVAL_MS` **on slow success as well** (or define `not_before` to include `last_send_completion + MIN_SEND_START_INTERVAL_MS`), thereby reusing the existing `not_before` term; define the §2 rebase target numerically (e.g. "shift `media_epoch` so that `deadline_{n+1} == completion_time`"); state whether the §2 rebase increments `pacer_rebases` and whether it is bounded by `MAX_REBASE_LATENESS_MS`; and state that a run with no qualifying clean segment is INVALID (row 2 not vacuously passable).

**Exit criterion.** `not_before` provably enforces `≥ completion + 18` after `send_call_duration_ms > 5.0` in the specified state; the slow path has a stated bound (or an explicit "unbounded by design, but reported and counted" with a PASS clause); the no-segment case has a verdict.

### M2 — A.12's `partial_zero_pad_samples` is anchored where the dominant underfill signature is structurally invisible, so A.13/A.15 row 18's starvation gate can pass while the client is starving.

**Evidence.** A.12:721 lists `whole_block_zero_fill_count` / `partial_zero_pad_samples` under "Playback / PortAudio (`audio_codec.py:192-239`)". In that callback, `_pull_mixed(self._mix_chunk)` (`audio_codec.py:218`) → `PcmFifo.pull(480)` returns either `None` (size == 0) or a **full-length** `np.zeros(n)` array with the unavailable tail zeroed (`audio_buffer.py:59-74`). `_pull_mixed` (`audio_codec.py:272-297`) then returns a full-length block (possibly `tts + music`), and `convert_output` (`audio_converter.py:130-148`) returns a full-length array or None. Therefore: `outdata.fill(0.0)` fires only when the FIFO is **completely** empty (`audio_codec.py:218-227`), and the "short return" branch (`audio_codec.py:226-229`) can only be triggered by a short `drain_output_buffer` (`audio_converter.py:150-167`) — a *resampler-buffer* residue condition, not the FIFO underfill.
